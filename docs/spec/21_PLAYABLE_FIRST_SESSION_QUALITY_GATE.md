# SPEC-21 — 最初の5分で「遊べる」倉庫ゲーム／初心者誘導／視覚品質ゲート
Version: 0.1 / Date: 2026-10-28
Status: [D]既定のカメラ/操作/ゲーム体験、[P]チュートリアル文言/演出/試験用収益、[U]原作の未検証細部
**この仕様はREVIEW-2026-10-28-001（ユーザー試遊0.5/10）のP0是正。**
`docs/spec/20_MOBILE_STATION_VERTICAL_SLICE.md` のS0/S1ブロックアウトを**技術土台**として再利用し、見た目や経営ゲーム完成の証明とは扱わない。

## 0. 成功体験・絶対に変えない決定
- ユーザーは参考ゲームと比較し、現状「全く似ていない、ゲーム性がない、何をすべきかわからない、3D品質が低い」と報告。元作品の**主要ルールと手動作業の楽しさ**を再現し、3Dは独自素材で同格を目指す。
- **自由歩行・WASD/左スティックは復活させない。** 固定ステーション/設備への直接3Dタップで即ビュー切替。
- カメラ切替だけで箱をテレポートしない。手動`Pickup`, `PlaceOnInspectionTable`, `PlaceOnExportGate`を明示し、全操作に実在するPackageIdを割り当てる。
- 初心者は「何をすればよいか」をゲーム画面で理解できなければ失敗。リッチな倉庫があっても棒立ちのデモは不合格。
- S0/S1の実テスト未通過は別途是正。現行PR #2をMergeする条件に「3Dを表示しただけでゲーム完成」と書いてはいけない。

## 1. 初回プレイのコア・ループ（実際に操作する）
| 順 | プレイヤーに見せる目的文言（仮） | 具体操作 | 完了条件（Domain） |
|---|---|---|---|
| 0 | 「荷物を検査して、正しい便に出荷しましょう」 | [作業を始める] | TutorialSessionを開始。操作説明が閉じてもタスクは保持 |
| 1 | 「荷台の箱をタップして、ひとつ受け取ろう」 | [搬入]へ/箱3Dタップ→[持つ] | `TransferParcel(source=TruckSlot,dest=HandSlot,parcelId)`成功、荷台描画が1個減る |
| 2 | 「検査台に箱を置こう」 | [検査]へ切替→3D台タップ→[置く] | `HandSlot→InspectionTableSlot`、持っている見た目は置かれるまでHandSlot内 |
| 3 | 「ラベルとルールを比べよう」 | 3D箱回転→ラベル拡大→貨物種別/架空国名・旗を見比べる | `InspectionDraft`にCargo/Countryの確認記録が残る。内部Truthはまだ見せない |
| 4 | 「合格なら緑、不合格なら赤のシールを貼ろう」 | プレイヤーが判断→シールをタップして貼付 | `SetInspectionDecision(Approved|Denied)`が箱に確定。間違いも選べる |
| 5 | 「対応する出荷口へ運ぼう」 | 箱を[持つ]→[出荷]→該当ゲートへ3Dタップ/配置 | 同一BoxIdが`InspectionTable→HandSlot→GateBuffer`と移る |
| 6 | 「発送を確定して結果を見よう」 | 出荷口の[出荷する]→内訳を表示 | SubmissionIdが1件作られ、正誤の数・価値・手数料・WalletLedgerイベントが重複なく確定 |
| 7 | 「はじめての出荷完了！次の荷物に挑戦しよう」 | 次の箱へ or 自由作業 | 新規セーブ／チュートリアル終了状態を保持 |

各段階で目的、対象のハイライト、操作ボタンを一致させる。`SelectStation`は所有を変更しない。シーンが空白になったり先の画面へ移っても`TutorialTaskId`を保持。

## 2. 初期ラベル・検査ルール
- まず`Cargo`と`Country`の2基準を本物として実装。正しい輸送区分/国旗と架空国名の一致を玩家が見て判断する。
- `ParcelTruth`と表示ラベルを別データにし、初期のFixtureとして少なくとも3種類:
  A: Cargo/Country正→Approved→適切な貨物ゲート
  B: Country名・旗の不一致→Denied→Rejectedゲート
  C: 不正なCargoラベル→Denied。あえて間違ったシール/ゲートにも入れられ、結果にペナルティが付く。
- 設計済みの重量Class、9桁シリアル検査、禁制品、スタンプは次のLicenseスプリントへ。未解放項目を強制判定しない。デモでダミー操作を「検査完了」と見せない。
- 有効な国名/旗は独自制作。原作の固有の国旗やブランドを複製しない。
- `InspectionDraft`はStation切替、アプリ中断、Save/Loadで保全。誤貼付もユーザーの意思によるゲーム結果として扱う。
- `Help`はルールの**読み方と比較手順**を教え、箱の正解そのものを自動暴露しない。初回の練習箱だけで例示解説可。

## 3. 出荷・収益 [U] 部分の取り扱い
- CargoMode/ExportGateId/GateSubmissionId/ShipmentId/TruckRunIdは別ID。地域倉庫CountryGateとは分離。
- ManualSubmit、AutoWhenFull、EndOfDayClearは別のコマンド/設定（SPEC-18）。初心者の最初の1箱を「容量16個揃うまで永遠に出荷不可」にしない。
- **チュートリアル専用の仮設定**`TutorialGateCapacity=1`かManualPartialSupportedプロファイルとする。[P]の出典タグを表示/データに残す。原作の全ゲートが容量1と主張しない。
- 旧倉庫の全曜日マスクが不明のため、初回の練習箱は`KnownTutorialOpenDay`（開発用固定Fixture）を指定。未知のAir/Maritime曜日に賭けない。
- 原作報酬の正確な式未確定。**TestFeePolicy**は仮値、費用と報酬のLedgerは本物の実装、見た目で加算しただけを禁止。ゲーム内に`試作版の報酬設定`と表示する。
- 最終結果のUIは`CorrectCount, IncorrectCount, CorrectParcelValue, IncorrectPenaltyValue, HandlingCharge, Total, SubmissionId`を表示し、加算を1回のみ確定。
- 最初のうちは無収入でもゲームが詰まらないテスト資金を`prototypeOnly`で用意。長期バランスの正確な数値は未確定とする。

## 4. 初心者に必要な情報アーキテクチャ
### 固定HUDとContextAction
- Top: 今日のゲーム内曜日/時刻・現在の貨物数・所持金（プロトタイプ数値なら明示）・現在の目的。
- Bottom: 通常は **[搬入][検査][出荷][倉庫][メニュー]** の5種。次のタスク以外を強調しない。その他機能（建設、契約、ショップ等）はメニュー内へ。
- 最重要の操作ボタンはタップしやすいサイズで、安全領域内。テキスト+アイコン（色のみで区別しない）。
- 初回の段階ごとに1つの主ボタン。無関係な機器や建設システムを先に展示しない。
- タップしても進まない場合は短い具体的エラー: 「持てるのは1箱です」「検査台に先に箱を置いてください」「このゲートは違う貨物です」。
- 上部のヘルプ/目的をタップすると、その時点の目的・アイコン・1画面の説明を表示。すぐ閉じて操作再開可。
- ショートテキストの日本語を使い、荷物の表面ラベルはタップで**拡大した鮮明な2D**表示。3Dモデルを近景でも読めるよう設計。
- TutorialGuideStateは`tutorialStepId, activeParcelId, highlightTargetId, isDismissed, completedSteps, lastErrorHintId`。Cancel・Save・Load・画面切替で保持。
- 目的の進行は実ゲームCommand成功のみで進める。HUDをタップしただけで「出荷完了」とはしない。

### 「何をすればよいか不明」問題を潰す受入チェック
- 初回画面で目標と最初に押す操作が**10秒以内に分かるか**をユーザーに実機で検証してもらう（達成保証ではない目標）。
- 操作説明を読まなくても、視覚的な強調・短い目的・正しいボタン導線から1箱の最初の移送ができる。
- 画面切替後、必ず「手に箱を持っている／台に置いてある／ゲートにある」のどこかが確認できる。
- 誤操作で箱消滅・レベルリセット・二重入金・行動不能にならない。
- 初回の出荷後に「何が正しく、何が違ったか」について納得できる内訳が見える。

## 5. 3D品質：見た目を「ブロックアウト」から「工業的リアリズム」へ
**完成度の判定はユーザーの実プレイ画面と参考画像の比較により行う。** 描画可能＝高品質達成ではない。

### 必須3Dヒーロー区画
**A. 搬入口とトラック**
- 倉庫の本物らしい寸法、シャッターの各レール/蝶番/安全ストライプ、荷台の奥行き、箱の封かんテープ、荷台内壁のリブ、荷台床パターン、荷下ろしスペース。
- トラック外側と路面は可視範囲に入る時のLOD別メッシュを持つ。箱を取った瞬間、対応する箱だけが消える/移る。

**B. 検査台**
- 金属製テーブル、秤または測定機（解放前なら視覚的な背景/ロック）、バーコード/伝票、照明/影、読み取り可能な文字・紙厚、箱の角やテープ、汚れの差、金属の適切なRoughness。
- 高品質な1箱へ描画予算を集中。カメラ/照明の角度はユーザーがラベルを読めることを優先。

**C. 出荷ゲートとコンベア**
- ゲート開口部と厚み、搬出口、金網、黄色の安全柵、脚/ローラー/ゴムベルト/接続機構、車両便の区分表示、容量/精算パネル（現在と直近結果を分離）。
- 建設では半透明ゴーストの向き/脚/ポートが実機と一致。方向が分かり、接続可否が視覚的に伝わる。

### 品質を保証する実制作フロー
1. 現状のS0/S1のシーンを**before**として画面記録。参照用3画像はルール/密度/材質の基準であって、テクスチャ/ロゴ/UIをコピーする対象ではない。
2. 区画A/B/Cそれぞれの**HeroAsset**をBlender等で独自に制作、または使用条件が確認できるライセンス付き素材から組み合わせる。すべてを手抜きCubeで完成扱いしない。
3. FBX/GLB/mesh/マテリアルの元データ・UV/PBR（normal/metallic/roughness/AO）・scale/LOD・license・Prefabの参照をManifestで管理。
4. 静的ベイク照明・安価な影/接地影とLightProbeを優先。不要な多数のリアルタイム光源やポストエフェクトでごまかさない。
5. iPhone横画面の解像度・SafeArea・日本語文字サイズで検証。カメラ/質感/密度/UIのBefore/After画像をPRに添える。
6. **デバイス向け描画を削って軽くしただけで視覚品質を合格としない**。プレイヤーがリアルに見える優先箇所は丁寧に残す。
7. 機能が本物でもアートが仮なら`GAMEPLAY_PARTIAL_ART_NOT_ACCEPTED`で区別。逆も同じ。

### 画質Profile
- `EDITOR_LOW`: Windows i7-7700/Intel HD 630の編集作業用。ベイク光源、低画面解像、遠景Cullを強く、編集の快適性優先。
- `MOBILE_BALANCED`: iPhone 13 Pro Maxの基本候補。近景ヒーロー区画だけ高品質、遠景をLOD/Cull。30fps安定を**計測して**目指す。
- `MOBILE_HIGH`: 高性能端末候補。実機計測により解禁、60fps達成を保証しない。
- Unity Remote 5で見た映像はPCレンダリング＋転送結果のため、**iPhone GPUでネイティブ処理した品質/熱/FPSと取り違えない**。ユーザーの今回の具体的な試遊方式は未確認。

## 7. 開発順（必要な工程を小PRへ）
**PR-A: Gameplay Foundation** `PackageOwnership`/Transfer/HandSlot/InspectionTable/GateBuffer/GameClock/Save。
**PR-B: Manual Inspection + Export** Cargo/Country、貼付/誤判定、Submitted Batch、Ledger、WrongGate/TutorialFixture。
**PR-C: Onboarding/UI** 0〜7のガイド、次の操作、ハイライト、初回成功、戻る、エラー説明。
**PR-D: Art Fidelity** A/B/Cヒーロー区画、モニター/ラベル、独自PBR、機器モデル、カメラ/光/美術QA。
**PR-E: Mobile Validation** Editor_LOWとMOBILE_BALANCED、実測、低熱/高画質の両立、iPhone上の操作。
上記は重要度順であり、実装は依存関係に応じて並行レビュー可能。どの段階でも「ユーザーが実際に遊べる」を偽装しない。

## 8. Codexが提出する証拠
- 実際にUnityのSceneを再生した映像またはスクリーンショット（EditorだけならEditorと明記）。
- 出荷までの一連の操作を記録した動画/ログ（荷物が実際に移動し、出荷結果が変わる）。
- UIに「次にすべきこと」が出ている画面と初回完了画面。
- 修正前/修正後の各Hero区画の画像3対。原作との比較は著作物コピーせず画質/情報/モデル密度の差を記録。
- EditMode/PlayMode/NativeDeviceで実際に走らせたテストとNOT_RUNの一覧。
- 端末の熱/FPS/描画条件（可能な場合）。**PCのIntel HD 630で低fpsを測った場合もiPhoneの性能へ転記しない**。
- ユーザーの再レビューと残課題をIssueに記録。開発者だけの「良くなった」主張では受入しない。
